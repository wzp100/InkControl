# 翻页动画 4 块原型预研（libeinkgpu 源码侧）

> 2026-11-08，工作区分析结论的代码化验证。面向 **Hisense A5 Pro 经典版 HLTE203T / Android 10**。
> 关联：工作区 `doc/翻页动画模块-冲突分析与共存方案.md` 第十二节「路线 4」，
> 以及 `docs/大功能后端支持清单.md` 5.1。

## 一、这次要回答什么

第十二节把「在 `libeinkgpu` 源码里重实现分块揭示」列为推荐预研路线，并留下三个待确认问题：

1. 墨控 HWC trampoline 有没有把原厂 `Update_Display_Image` 入口留在 native 可达处？
2. `hookUpdate` 能否稳定区分「整屏 GC16」与其它帧？
3. 一个只在整屏 GC16 生效的 4 块原型，能否在不破坏波形时序的前提下跑通？

本次结论（含当日上机实测，见第七节）：**① 已确认可行；② 只在第三方翻页动画 HWC 上成立，在墨控 patched GPU HWC 上被实测推翻；③ 仍然是「默认只观测」的骨架，但已在真机跑通门控命中、4 块几何与提交计划打印，没有接管传输、没有影响显示。**
原型代码在 `native/service_pageanim.hpp`，接入点只有 `native/service_gpu.cpp` 的 `hookUpdate` 开头一行。

## 二、三个已确认的事实

| 问题 | 结论 | 依据 |
| --- | --- | --- |
| 原厂提交入口 | **native 侧直接可调用，无需改 HWC 二进制** | `hookUpdate` 的 else 分支本来就是 `reinterpret_cast<int(*)(void*,void*)>(base+0x95dc4)(entry,ctl)`；翻页动画引擎要靠段内保存的函数指针间接调用，墨控反而更直接 |
| 控制结构 | **`hookUpdate(void* entry, void* ctl)` 的 `ctl` 与翻页动画引擎门控读的 `x1` 是同一份结构** | 引擎读 `+0xbc/+0xc0`（1440/720）、`+0x270/+0x278/+0x280`、`+0x15c/+0x160`；`hookUpdate` 读的是同一组偏移（`field<uint8_t>(ctl,0x15c)`、`field<int>(ctl,0x270)`、`0x160` 等） |
| EPD 波形方式 | **只在第三方翻页动画 HWC 上可读；墨控 patched GPU HWC 上不适用** | `base+0x9c2358` 是第三方注入段的私有 BSS 地址；GPU 库同一偏移实测读到 `0x09090908`（填充图案），见第七节 |

也就是说，第十二节里最担心的「拿不到原厂传输函数指针」不成立 —— 这是路线 4 相对路线 2/3 最大的优势，现在有了代码级证据；而「照抄引擎门控」这条路则被上机实测否定，正式实现必须改用墨控自己的 `ctl` 语义。

## 三、原型做了什么

`native/service_pageanim.hpp`（自包含、`-Wall -Wextra -Werror` 编译通过）：

- **门控** `inspect()`：整屏 720×1440、`base+0x9c2358` ∈ {0x201, 0x203, 0x603}、
  `ctl+0x270==1 && 0x278==0 && 0x280==0`，外加属性 `armed=1`（模拟 resident 的
  白名单命中 / 已武装）。**这组条件是从翻页动画引擎照抄的，只作对照**；
  上机证明在 GPU HWC 上恒不成立，实验时用 `force_gate=1` 跳过 EPD/clean 两项。
- **观测** `observe=1` 时每 64 帧采样打印 `PAGEANIM_OBS`（宽高、mode、frames、
  epd、full/gc16/clean/armed），用于确认不同 HWC 上 `ctl` 的真实取值。
- **4 块几何** `block()`：默认横向切四条（每条 720×360），
  `sys.inkcontrol.pageanim.style=1` 时纵向切四条（每条 180×1440）。
- **提交骨架** `submitBlocks()`：打印将要对 `base+0x95dc4` 发起的 4 次调用，
  带 `entry` / `ctl` / 函数指针与各自矩形。
- **默认完全不接管**：`probe()` 只有在 `debug.inkcontrol.pageanim.proto=1` 时才进入；
  命中后如果 `sys.inkcontrol.pageanim.submit` 没开，就只输出 `PAGEANIM_HIT` / `PAGEANIM_BLOCK` 日志，
  返回 `false`，`hookUpdate` 继续照常跑 GPU 波形流水线。属性一个都不设时，
  每帧只多一次 `__system_property_get`，产物行为与原来一致。

开关：

```sh
# 一律用 debug.* 前缀：上机实测 composer HAL 读得到 debug.*，读不到同名 sys.*
# （getprop 能看到，__system_property_get 拿到空值）；flag() 也保留 sys.* 兼容回退。
setprop debug.inkcontrol.pageanim.proto 1       # 进入预研分支（总开关）
setprop debug.inkcontrol.pageanim.observe 1     # 采样打印 ctl 字段（可选）
setprop debug.inkcontrol.pageanim.armed 1       # 模拟白名单命中
setprop debug.inkcontrol.pageanim.force_gate 1  # 跳过照抄来的 EPD/clean 门控（实验用）
setprop debug.inkcontrol.pageanim.style 0       # 0 横向 / 1 纵向
setprop debug.inkcontrol.pageanim.submit 1      # 打印 4 次调用计划（仍不真调用）
logcat -s EinkPageAnim                          # PAGEANIM_HIT / BLOCK / SUBMIT_PLAN / OBS
# 收尾：把上面所有属性设回 0，或重启（属性不持久），原型即完全零影响
```

**`submit=1` 仍然只打印计划**：`submitBlocks()` 不改写 `ctl`、不调用 `stock`，
`probe()` 恒返回 `false`，`hookUpdate` 继续跑完整 GPU 波形流水线。

## 四、还没解决的（上机前必须补齐）

1. **`ctl` 里矩形字段的偏移未知。** 引擎是「把一次整屏传输拆成若干块依次送驱动」，
   但公开可读的偏移只覆盖了宽高与相位标志，没有可确认的 `x/y/w/h` 四元组。
   `PAGEANIM_RECT_OFFSET` 目前是 0（`writeRect` 空操作），上机前要用 IDA 对
   `0x6800d94` 的分块循环逆向一次，确认它到底改了 `x1` 的哪几个字段。
2. **原厂状态机按「一次整屏」设计。** `hookUpdate` 后面要更新 `ringRecords[slot]`、
   `verifyStep`、`gpuCancelRollingWave`、`motionExtend` 等；重复调用
   `base+0x95dc4` 会让帧计数、LUT 步进与波形时序错乱。真接管必须在
   `rollingProducer` / `eligible` 都未启动时、且整帧二选一地跳过 GPU 流水线。
3. **armed 的来源还没接。** 现在用属性模拟；正式实现要么让
   `a5pro-resident` 继续写、要么改由墨控的 system_server 钩子按前台包名下发
   `sys.inkcontrol.pageanim.reader`，否则白名单语义落不了地。
   §10.4 里 `reader` 字段（control-once 只能填 1、只有 resident 写真实前台标识）
   是引擎放行失败的可疑点，墨控自己实现时不要照抄这个约定。
4. **双重处理互斥。** 命中动画的那一帧必须完全跳过 GPU 量化与波形，
   否则会出现半截波形 + 半截分块；这一点要在原型真正提交前先写成断言。

## 五、上机验证顺序（计划；执行结果见第七节）

1. 只开 `proto=1`，不开 `armed`：确认滚动 / A2 / 极速下**没有任何** `PAGEANIM_HIT`，
   即门控不会误伤局部刷新。
2. 开 `armed=1`，在白名单阅读器里整页翻页，确认 `PAGEANIM_HIT` 只在整屏 GC16 出现，
   `epd=0x203` 一类的日志与 `WAVE … mode=` 对得上；刷新键那次面板级 `clear` 不应命中。
3. 逆向补齐 `PAGEANIM_RECT_OFFSET` 后，先在 GPU 显示后端关闭的状态下试 4 块提交，
   用 `setprop debug.eink.mode.log 1` 看是否出现多段 `clear=`。
4. 再开 GPU 后端，验证非命中帧的波形日志与命中帧的分块日志互不干扰。
5. 全程盯 `sys.inkcontrol.ready`、composer pid 与 `runtime.json`，异常立刻
   `setprop debug.inkcontrol.pageanim.proto 0` 回到原路径（不需要重启，属性即时生效）。

## 六、风险与边界

- 这是**预研骨架，不是可用功能**：默认任何属性都不设时零影响；
  `submit=1` 也只打印计划，不会改写 `ctl`、不会重复提交。
- 真正的分块提交一旦打开就碰 composer 的传输路径，可能黑屏或波形错乱，
  必须在有备用机 / 异地备份的前提下做，且随时可关属性回退。
- 原型不解决「刷新键的水波纹全刷」：那条路径是面板级 `clear ghosting`，
  两个引擎都拦不到（见共存方案 §11.1）。
- 第三方算法来源仍是 nuku 的社区作品，整合与署名边界见 `NOTICE.md`。

### 由此改写的结论

1. **路线 4 上机可行**：同一份 `libeinkgpu.so` 里 GPU 波形与 4 块原型可以共存，
   只观测时零影响，且不需要改 HWC 二进制就能拿到原厂传输入口。
2. **但不能复用翻页动画引擎的门控**。`base+0x9c2358` 与 `ctl+0x270/0x278/0x280`
   的约定属于另一份 HWC；墨控 GPU 路径里 `0x280` 是 blank、`0x270` 是 reset，
   `hookPreprocess` 的条件恰好是 `blank!=0 && reset==0 && transition==0`，与引擎相反。
   正式实现必须按 `einktransition::Control`（`mode/phase/frames/region`）重新定义
   「整屏 GC16」，不要再引用第三方注入段的私有 BSS 地址。
3. 第四节的四项未解决问题**全部保留**：矩形字段偏移、原厂状态机重复提交、
   armed 的真实来源（前台包名）、命中帧必须整帧跳过 GPU 流水线。
4. 本次**没有**做真正的 4 块提交，也没打开 `PAGEANIM_RECT_OFFSET`；
   所有实验属性已设回 0。要恢复翻页动画配置，用备份里的 `rollback.sh` + 完整重启。

## 八、融合尝试：把分块揭示重写到 GPU 波形的依赖上

第七节证明了「照抄门控 + 重复调用原厂传输入口」这条路的三个死结：私有 BSS 地址不属于墨控 HWC、
`ctl` 矩形偏移未知、原厂状态机按一次整屏设计。**换个依赖就能绕开全部三个**：

| 第三方翻页动画引擎 | 墨控 GPU 后端里的对应依赖 |
| --- | --- |
| 占住 `0x92fe4`（`Update_Display_Image`）拆块 | 不需要：`hookUpdate` 每帧本来就会被调用，波形帧序列 `segment.total` / `localFrame` 就是天然的「阶段」 |
| 改写 `x1` 的矩形字段逐块送驱动 | 不需要：`request.gpuIndices` 是逐像素 LUT 索引缓冲，按 y 条带改索引是纯数据操作 |
| HWC BSS 里的 EPD 波形白名单 | 不需要：`ctl+0x15c` 的 `mode`、`+0x160` 的 `total`、`+0x2c8` 的 `region` 就是墨控自己的门控语义 |
| 独立挂载一份 `hwcomposer.pageanim.so` | 不需要：逻辑全在 `libeinkgpu.so` 源码里，HWC 只有一份 |

于是「4 块揭示」被重写为**一次整屏波形的 4 个条带相位**：

```
localFrame = total - remaining          （service_transitions.hpp::Segment）
band       = localFrame * bands / (total + 1)
条带 i 的 y 范围 = [i * 1440/bands, (i+1) * 1440/bands)
```

`native/service_fusion.hpp` 实现这套门控与相位计算，接入点仍是 `hookUpdate` 开头一行，
属性全部缺省为关。它与第七节原型的关键差别：**门控不再引用第三方 HWC 的任何地址**，
也**不重复调用 `base+0x95dc4`**（日志里打印它只是为了说明「这条入口可达但本路线不用」）。
因此不存在 HWC 单文件争用，也不会打乱 ring 计数与波形时序。

### 本版边界与真正生效的落点

本版只观测：`probe()` 恒返回 `false`，`hookUpdate` 照常跑完整 GPU 波形流水线，
命中时输出 `FUSION_HIT` / 4 条 `FUSION_BAND`（y 范围与起止帧），
`plan=1` 时逐帧输出 `FUSION_PHASE`，`observe=1` 时采样打印 `FUSION_OBS`。
要真正产生「从上往下分块揭示」的视觉效果，只需在 `gpuBeginWave(request)` 之前
按当前 `band` 把 `request.gpuIndices` 里非当前条带的索引置为中性值 ——
这是纯数据遮蔽，不改 `ctl`、不碰传输函数、不需要重启显示 HAL。
该步骤会改变实际显示，属下一阶段，需在备用机 / 完整备份下单独验证。

### 属性（HAL 只读得到 `debug.*` 前缀）

```sh
setprop debug.inkcontrol.fusion 1          # 进入融合分支
setprop debug.inkcontrol.fusion.armed 1    # 模拟白名单命中
setprop debug.inkcontrol.fusion.observe 1  # 采样打印 ctl 字段
setprop debug.inkcontrol.fusion.plan 1     # 逐帧打印条带相位
setprop debug.inkcontrol.fusion.bands 4    # 4..32，默认 4
logcat -s EinkFusion
```

### 验证标准与上机结果（2026-11-08，产物 `out/r26fusion`）

1. 属性全 0 时零影响，GPU 波形日志与 `runtime.json` 的 `gpu_errors` 不变；
2. 打开融合属性后，整屏波形帧出现 `FUSION_HIT` + 4 条 `FUSION_BAND`，
   且 `EinkGPU` 的波形日志仍在同一批帧里出现 —— 证明两条逻辑同帧共存；
3. composer pid 不变、无 `error` / `disable_hwc`、截图显示正常；
4. 条带相位必须随 `localFrame` 单调递增，且 `total` 与日志里的 `frames` 对得上。

实测（日志样本见本机 `temp/backup-20261108-compat/fusion-logcat-sample.txt`）：

- `FUSION_OBS w=1440 h=720 mode=5 total=38 frame=15 region=0 blank=1 reset=0 trans=0
  full=1 wave=1 nonlocal=1 armed=1` —— 门控条件全部由墨控自己的 `ctl` 语义满足，
  不再依赖任何第三方 HWC 地址。
- `FUSION_HIT mode=5 total=38 bands=4 stock=0x7efce7adc4 (unused)`，
  4 条 `FUSION_BAND`：`y=0/360/720/1080`、各 `h=360`、
  `frames=0..8 / 9..18 / 19..28 / 29..38`；`mode=8 total=9` 的另一波也命中，
  分成 `0..1 / 2..4 / 5..6 / 7..9`。`stock` 标注 unused，确认本路线不调用原厂入口。
- 共 `FUSION_HIT` 25 次、`FUSION_BAND` 97 条、`FUSION_PHASE` 518 条；
  相位随帧单调递增（frame 17→band 1、20→band 2、30→band 3），
  同期 `EinkGPU MODE_SEEN 513` 仍在，证明两条逻辑同帧共存、未互相接管。
- composer pid 3683 全程不变、`ready=1`、`gpu_errors=0`、`helper_loaded=true`、
  无 `error` / `disable_hwc`，真机截图无花屏或条带残影；实验属性已全部归零。

**结论**：「让一者的逻辑重写到另外一者的依赖上」这条路在**架构上**成立 ——
融合后不再有第二份 HWC、不再争 `0x92fe4`，`pageanim.master` 从「开机选库」变成
运行时开关：与 `display.gpu` 同时为 1 时仍挂 GPU 后端，切换不需要重启，GPU 的
分模式算法与波形动画也不停用。当时**视觉级共存还没做到**（见第九节；该结论已被
第十节修正并实现，`drive` 现已自动下发）。
代价是分块揭示必须由墨控 GPU 波形层重新实现，第三方注入段与 `a5pro-resident` 不能复用。

## 九、已知问题：分带揭示与面板级全刷（2026-11-08 实机复现）

### 现象

`display.gpu=1` 与 `pageanim.master=1` 同时启用、`drive=1` 真正驱动 `bandDirection` 后，
连按两次物理刷新键，屏幕变成**大面积黑底、只剩部分白字**。把 `debug.inkcontrol.fusion*`
全部归零并强制重绘后立即恢复正常。期间 `gpu_errors=0`、composer pid 不变、
无 `ROLL_BEGIN_FALLBACK` / `CONTROL_VERIFY_FAIL` —— 不是崩溃或波形回退，
而是画面被定格在波形中间态。

### 根因

着色器（`service_waveform.hpp`）的分带逻辑：

```glsl
if(bandDirection!=0u){
    uint delay=(bandDirection==2u?719u-row:row)/48u;   // 15 带，延迟 0..14 帧
    drive=frameNumber>=delay && frameNumber-delay<=bandFrames;
    f=frameNumber-delay;
}
...
else if(!drive){color=vec4(...templ...);return;}       // 未驱动区域输出模板旧像素
```

- 初版把 `bandFrames` 设成 `spacing/4`（默认 spacing=12 → 3）。38 帧波形走到后期，
  绝大多数行的 `frameNumber-delay > 3`，于是 `drive=false`，帧缓冲里是 `templ` 而不是新图。
- 刷新键走 `SurfaceFlinger.forceClearGhosting()` → 面板级 `clear ghosting`，
  **不产生新的合成帧**（共存方案 §11.1 已确认），直接把当前帧缓冲重刷到屏上，
  于是「分带中间态」被定格成黑底。
- 第三方翻页动画引擎不碰这条路径，所以原版没有这个现象；这是把揭示逻辑搬进
  GPU 波形层之后新引入的交互。

### 处置

1. `drive()` 的 `bandFrames` 改为 `activeFrames-1`（`validWave` 约束下唯一能让每条带
   一直驱动到末帧的安全值），保证波形收敛成完整新图。
2. `ic_properties()` **不再自动下发 `fusion.drive=1`**：即使两个开关同时开，
   融合也只观测、不改显示；架构上的运行时共存仍然成立。
3. `pageanim.spacing` 暂不映射：着色器把带间延迟写死成 `row/48`，可调的只有
   `bandFrames`，而它必须取安全值。要恢复「速度可调」得把 48 做成 uniform。
4. 手动开 `drive` 做实验时，务必先确认没有刷新键 / 自动刷新同时触发；
   出现黑屏立即把所有 `debug.inkcontrol.fusion*` 归零并强制重绘，属性即时生效、无需重启。

### 结论修正

第八节说的「架构上成立」仍然成立，但当时判断**视觉级共存尚未通过**：分带揭示的
视觉生效被禁用，等待「波形末帧收敛 + 面板级 clear 规避」方案验证后再启用。

> **本节结论已在第十节被推翻并修复**：黑屏的真实成因是 `!drive` 送出了控制模板的
> 原始驱动字节，而非「驱动 + 刷新键」的组合；本轮已改为中性驱动字节、并按 `bandTail`
> 延长总帧数解决「刷新不干净」，`drive` 恢复自动下发。本节保留为当时的判断记录。

## 十、视觉级共存：修正误判与「刷新不干净」的真正修复

### 10.1 第九节的因果不成立

第九节把黑屏归因于「融合驱动 + 刷新键」，但当时止血是**关融合属性与强制重绘同时做**的，
两个变量一起变，因果并没有隔离。用户随后指出：黑屏前他是手动点了两次智墨键
（系统设置里把智墨键单击设成了刷新）。复查日志确认这条链是：

```
HmctWindowManager: mAIKeyShortPressTimedOutRunnable mEinkKeyClickValue = 3
HmctWindowManager: forceClear
SurfaceFlinger:    epd forceClearGhosting        ← 面板级全刷，不产生新合成帧
EpdManagerService: updateEpdMode 0x203
```

按同样的操作序列做对照实验（`drive=0` 与 `drive=1` 各连按两次刷新键，12 帧高频抓图）：

| 组 | 条件 | 暗像素占比 |
| --- | --- | --- |
| 基线 | 稳定首页 | 10.3% |
| A | `drive=0` + 两次刷新键 | 2.6% / 2.1% |
| B | `drive=1`（真实触发 6 次 `FUSION_DRIVE`）+ 两次刷新键 | 2.6% / 2.1%（与 A 逐像素一致） |

结论：**在收敛参数下，分带驱动 + 连按刷新键并不产生黑屏**。上一轮的 `r26safe`
其实已经修好了黑屏（`bandFrames` 从 `spacing/4=3` 改成收敛值），但我同时把
`drive` 一起关了，于是那个修复从未在启用状态下被验证过。教训：**一次只改一个变量，
止血时也要记清哪个动作真正起效。**

### 10.2 「刷新不干净」的根因：只错峰、不延长

用户启用后看到的残影是**旧页文字的浅灰重影**，位置成片。根因在分带的时间预算：

- 着色器里 `f = frameNumber - delay`，每条带从自己的启动帧开始读 LUT；
- 但 `totalFrames` 仍是 `activeFrames + 1`，波形并没有因为错峰而变长；
- 于是 `delay` 越大的带，越会在**LUT 尾部被截断**——最后几帧收敛帧根本没跑到，
  像素停在中间灰阶，旧页就留下浅灰残影。

`bandFrames` 取 `activeFrames-1` 只让 `!drive` 分支少走，并没有解决「帧数不够」。

### 10.3 修复：迟启动 + 总帧数等量延长

1. 着色器新增 `bandRows` / `bandTail` / `bandStyle` 三个 uniform：
   - `bandRows = 720 / pageanim.bands`，分块数量真正生效；
   - `bandTail` 是「为错峰额外延长的帧数」，`delay = bandIndex * bandTail / (steps-1)`；
   - `bandStyle` 把 `pageanim.style` 的六种展开（横/纵/斜/反斜/环绕/中心）折成
     一维揭示次序 `coord`，再由 `coord/rows` 得到带号。
2. `totalFrames = activeFrames + bandTail + 1`（`validWave` 已放宽该约束，`bandTail <= 24`）。
3. `frame 0` 的原厂调用之后，`einkfusion::extendTail()` 给 `ctl+0xc8` 与 `ctl+0x160`
   同时加 `bandTail`——帧号 `total - remaining` 不变，但 A2 循环会多跑 `bandTail` 帧，
   每条带因此都能从 LUT 第 0 帧走满 `activeFrames` 帧，末帧收敛。
   失败或提前终止时 `restoreTail()` 撤回，避免原厂用扩展后的帧号越界访问 LUT。
4. `!drive` 区域输出**中性驱动字节 0**（保持当前像素），不再把控制模板的原始
   驱动字节送出去——那是第九节黑屏的直接来源，也顺手彻底关掉了。

`bandTail` 取值：`分带数 × 3/4` 作基数，再按 `spacing/12` 缩放，夹在 `4..16`
（与 motion 延长同量级），并受 `158 - activeFrames` 上限约束。

### 10.4 参数与效果

| bands | spacing | bandTail | 总帧数 |
| --- | --- | --- | --- |
| 4 | 12 | 4 | active+5 |
| 12 | 12 | 9 | active+10 |
| 12 | 40 | 16 | active+17 |
| 32 | 12 | 16 | active+17 |

代价是整屏刷新多几帧（约 10~17 帧，几十毫秒），换来每条带走完 LUT、画面干净。
这是「分阶段揭示」的必然成本：揭示要分先后，先后就必须有额外的时间预算。

### 10.5 观测口径提醒

`screencap` 抓的是 Android 合成层，**不是 EPD 物理送屏内容**。判断「刷新是否干净」
只能用物理屏目视，或抓 GPU 波形帧（`readingCaptureWindow` 的位图）。本轮 A/B 实验的
截图只能证明合成层无异常，物理效果仍需上机目视确认。

## 十一、触发范围：白名单闸门（0.2.6-r26 修复）

### 11.1 现象

融合模式启用后，**所有整屏刷新都会播放一次分带揭示**：唤出 E-Ink 快捷面板、
在可滚动页面上下滑动、打开新页面，全都出现「斜向扫过」的果冻感。
把 `pageanim.spacing` 调到 40 时最明显。

### 11.2 根因：把「按需武装」简化成了常量 1

原版翻页动画的触发范围由三件事共同决定：**常驻端读触摸/按键做手势识别**、
**前台应用在 `pageanim.readers` 名单里**、`pageanim.debounce` 去抖。
融合路线没有常驻端，第一版直接把 `debug.inkcontrol.fusion.armed` 写成常数 1，
`pageanim.readers` 也完全没接 —— 于是 `drive()` 的门控只剩「整屏 + GPU 波形族 + 非区域叠加」，
等于给每一次全屏 GC16 都开了分带。

实测（`out/r26tail`，style=2 / spacing=40）：

| 场景 | `FUSION_DRIVE` | `active` |
| --- | --- | --- |
| 唤出快捷面板 | 3 次 | 38 |
| 阅读器内上下滚动 | 每次滑动 1~2 次 | 9 |
| 墨控内滑动/启动 | 每次 1 次 | 38 |
| 真正翻页 | 1 次 | 38 |

### 11.3 为什么不能靠波形字段区分

抓 `FUSION_OBS` 对比滚动与翻页：`w=1440 h=720 mode=8 region=0 blank=0 reset=0 trans=0
full=1 wave=1 nonlocal=1` —— **除帧数外所有字段完全一致**。`mode` 恒为 8，
所以「用 mode 排除滚动」不成立；而在「清晰」模式下滚动同样是 GC16，
「用 `active` 阈值排除滚动」也会误伤。融合层拿不到触摸事件，
**唯一可靠的判据就是原版用过的那个：前台应用是否在目标阅读器名单里**。

### 11.4 修复

1. **system_server 侧**（`features/fix/Hook.java`）：复用已有的前台切换钩子
   `EpdManagerService$1.begigResumeActivity`，在门控之前调用 `updateFusionReader(pkg)`：
   比对 `RuntimeConfig.value("pageanim.readers")`（逗号分隔），命中写
   `debug.inkcontrol.fusion.reader=1`，否则写 `0`。只在包名变化时写一次；
   配置变更时清缓存，下次前台切换按新名单重算。
2. **composer HAL 侧**（`native/service_fusion.hpp`）：`Frame` 新增 `reader`，
   `drive()` 与 `probe()` 都要求 `reader=1`。
3. **后端**（`backend/lib/common.sh`）：融合开启时只在属性尚未写过时给初值 `0`
   （即「默认不触发」），避免 `inkctl apply` 冲掉当前前台状态；融合关闭时一并清 0。

名单为空时按 Guide 的既有语义处理：**不触发**。所以升级后如果名单是空的，
翻页动画会完全不出现 —— 这是与原版一致的行为，不是故障。

### 11.5 仍存在的边界

融合路线没有手势识别，所以**同一白名单应用内的整屏刷新也会播放**，
包括上下滚动、弹窗、页内重绘。`pageanim.touch` / `pageanim.keys` /
`pageanim.debounce` 三项在融合模式下不参与判断，只在独立库模式（未开 GPU 后端）生效。
Guide 文案已按这个口径改写。

要做到「只翻页、不滚动」，需要拿到触摸事件。可选方向：
- 在 system_server 侧 hook `InputManagerService` 的输入分发，记录最近一次手势方向，
  再写一条 `debug.inkcontrol.fusion.gesture` 属性 —— 风险在 input 关键路径，需单独评估；
- 或恢复一个只做手势识别的轻量常驻端（不碰注入段，只写属性）。

### 11.6 与「动画」互斥：全刷扫过为什么变成斜向

「全刷扫过」（`motion.gc_clear` → `gcsweep`）和融合分带都靠波形时序表达：

| | 表达方式 |
| --- | --- |
| 全刷扫过 | 起跑帧图 `request.cpuStartMap` + `maxDelay`（每像素错开几帧开始扫） |
| 融合分带 | `request.bandDirection` + `bandRows/bandTail`（着色器按行/格延迟） |

`hookUpdate` 里融合分支位于 `motionDecide` 之后，并且无条件 `motionMax=0`，于是 gcsweep
的起跑图被丢掉、只剩斜向分带 —— 表现就是「黑带扫过的方向被翻页风格带成斜的」。
现在改为 **`motionMax>0` 时融合不介入**：用户为该场景显式选了动画，就不该再叠加分带。

顺带修掉一个上游遗留：`gcsweep` 的方向原先只在 App 侧写 `spread`、在 native 侧
`strcpy(sweep.dir,"ltr")` 写死，所以「擦除方向」对它完全无效。现在属性格式改为
`gcsweep <spread> <dir>`（旧格式仍按 ltr 解析），方向由新增的「全刷扫过方向」
（`motion.gc_direction`）控制，`auto` 保持原厂「从左向右」。着色器里 `kind==2`
本来就支持 `ltr/rtl/ttb/btt` 四种，只差把值传下来。
